# MineMod: 100 пунктов до production

Дата исходного плана: 4 октября 2026 года. Порядок дальнейшей работы актуализирован 5 октября 2026 года. Статус: выполняется по поручению пользователя; каждый завершённый пункт получает отдельный коммит `roadmap(NNN)` и evidence. Исходный план сам по себе не подтверждает выполнение.

Цель: выпустить MineMod Studio и связанный генератор как надёжный инструмент, в котором пользователь вместе с Codex или Claude Code создаёт, редактирует и проверяет Minecraft-модели, а затем получает работающий Fabric-мод с исходниками и доказательствами качества.

## Основание и текущая готовность

План подчиняется [ADR-0004](decisions/0004-fabric-1.20.1-production-baseline.md) и [Fabric-first MVP plan](FABRIC_FIRST_MVP_PLAN.md). Основной игровой target — Fabric 1.20.1 / Java 17. Приложение развивается на существующем Electron/TypeScript-стеке; первый desktop-релиз ориентирован на проверенную Windows x64. Другие ОС и загрузчики требуют отдельных проверок и не получают обещания готовности автоматически.

Исходный снимок при составлении плана, до выполнения пунктов; локальный отчёт `output/verification/STUDIO_BUILD.json`. Новые результаты перечислены у закрытых пунктов:

- Studio 0.5.1 имеет тёмную тему, редактирование геометрии, покраску/UV, варианты, историю, MCP, экспорт и обзор модели с нескольких сторон. Локальная сборка и проверки упакованного редактора прошли.
- Три новых дизайна оружия остаются художественными черновиками. Их качество ещё не принято пользователем; успешные технические проверки не заменяют эту оценку.
- Экспорт авторских моделей ещё не означает проверенную интеграцию в `ModSpec → JAR`. Самостоятельные сеансы генерации установленными Codex и Claude Code для текущей версии требуют отдельного доказательства.
- Fabric-компилятор поддерживает базовый контент и оборудование; обычные предметы и блоки всё ещё используют placeholder. Полноценные авторские блоки, существа и экраны нельзя считать готовыми.
- Игровые задания текущего `phase-0.yml` используют старые regression-targets, включая Fabric 26.2 / Java 25. Нужен отдельный обязательный CI для production-target 1.20.1 / Java 17.
- Build runner сейчас требует Linux x64. Проверка Windows-приложения и сборка игрового мода являются разными операциями.

Открытый пункт может означать доработку существующей функции или доказательство её production-готовности. Закрывать его следует по проверке точной версии и приложенному evidence, а не по наличию похожего кода.

## Порядок и границы выпусков

Номера ниже — постоянные IDs задач, а не требование выполнять их строго по порядку. В текущем трекере отмечены 34 завершённых пункта из 100; это счёт задач, а не процент production-готовности. Статусы и существующие evidence сохранены. При подготовке очередного кандидата нужно проверить применимость прошлых результатов к его точной версии.

Ближайший порядок работы учитывает главный запрос пользователя — улучшить художественное качество моделей и удобство приложения:

|---|---|---|

| 4. Текстура выбранного оружия | 51–57 | Согласованные пиксельные кластеры, материалы и UV. Исходный и новый варианты сравниваются при одинаковом масштабе; точный кандидат получает художественное review. |
| 5. Первый настоящий авторский блок | 58–60, 63–65 | Отдельный block target, текстуры граней, проверка повторения 3×3, состояния и collision. Блок проходит экспорт и интеграцию с корректным поведением размещения и разрушения. |

| 7. Beta редактора и обратная связь | 11, 77–90, 92–94, 98 | Закрыты применимые проверки зависимостей, безопасности, сохранения и производительности. Новый пользователь самостоятельно подключает агента, создаёт модель и экспортирует её; дефекты пилота исправлены. |

Проверки 71–90 сопровождают каждое изменение соответствующего компонента. Очереди могут идти параллельно по независимым задачам, но интеграция зависит от принятого asset-контракта и review. Подключение Codex/Claude строится на разрешённых MCP-операциях. Для разработки и проверок использовать CLI, API и отдельные скрытые тестовые экземпляры, сохраняя возможность пользователя активно работать на ПК.

- **Редактор beta:** сохранение и восстановление, оба агента, понятная ручная правка, принятые человеком модели и проверенный экспорт. Это ещё не готовность всего генератора.
- **Beta с Minecraft:** авторское оружие и блоки проходят явную интеграцию, clean build, client/server-проверки и художественную оценку в игре.
- **Production всего проекта:** все 100 пунктов закрыты применимыми доказательствами, включая Tidecaller и пять dogfood-проектов из текущего Fabric-плана.

Сроки и исполнителей нужно оценить после пунктов 4, 6 и 10. Количество пунктов не является оценкой объёма: анимации, игровые экраны и сборочная инфраструктура существенно крупнее отдельных улучшений интерфейса.

## Этап 1. Продукт, scope и критерии готовности

1. [x] **Зафиксировать контракт первого релиза.** Назвать поддерживаемые Windows x64, Fabric 1.20.1 / Java 17 и точные ограничения. Приёмка: одна опубликованная матрица соответствует реально проверенным окружениям. Evidence: [release contract](production/RELEASE_CONTRACT.md), [проверенные локальные artifacts](production/evidence/studio-0.5.1-local.json); коммит `roadmap(001)`.
2. [x] **Описать основные пользовательские сценарии.** Новичок создаёт модель через агента; автор мода редактирует её вручную и интегрирует. Приёмка: оба пути имеют начало, ожидаемый результат и обработку ошибок. Evidence: [два сценария и восстановление](production/USER_SCENARIOS.md); коммит `roadmap(002)`.
3. [x] **Разделить три уровня выпуска.** Редактор beta, beta с игровыми ресурсами, production всего генератора. Приёмка: для каждого уровня есть отдельный список обязательных доказательств без обещаний будущих функций. Evidence: [R1/R2/R3 и их blockers](production/RELEASE_GATES.md); коммит `roadmap(003)`.
4. [x] **Составить актуальный аудит возможностей.** Сопоставить документацию, код и отчёты: готово, частично, не реализовано, не проверено. Приёмка: у каждого утверждения есть ссылка на источник или проверку. Evidence: [capability audit](production/CAPABILITY_AUDIT.md), [команды и hashes](production/evidence/audit-004.json); коммит `roadmap(004)`.
5. [x] **Подготовить набор контрольных брифов.** Оружие, броня, строительный блок, декоративный объект и существо с определённым стилем. Приёмка: одинаковые задания можно повторять на разных версиях системы. Evidence: [пять versioned брифов](../fixtures/production/control-briefs.v1.json), [протокол повторения](production/CONTROL_BRIEFS.md); коммит `roadmap(005)`.
6. [x] **Назначить пороги приёмки.** Определить художественную rubric, обязательные тесты, бюджеты ресурсов и допустимую задержку на выбранных ПК. Приёмка: пороги записаны до оценки кандидата. Evidence: [acceptance policy](production/ACCEPTANCE_POLICY.md), [thresholds v1](production/acceptance-policy.v1.json); коммит `roadmap(006)`.
7. [x] **Зафиксировать границы MVP.** Произвольный Java/shell, generic mesh, физика, marketplace и равенство всех платформ остаются вне первого выпуска. Приёмка: неподдерживаемое действие получает точную диагностику. Evidence: [scope/diagnostics](production/MVP_SCOPE.md), [Linux negative suites и Windows MCP](production/evidence/scope-007.json); коммит `roadmap(007)`.
8. [x] **Согласовать развитие compatibility packs.** Любая смена loader/API/JDK создаёт новую проверяемую revision. Приёмка: обновление не меняет существующий trusted pack скрытно и имеет миграционный отчёт. Evidence: [immutable revisions и migration protocol](production/COMPATIBILITY_POLICY.md), актуализация старого GA roadmap; коммит `roadmap(008)`.
9. [x] **Определить роли приёмки.** Зафиксировать ответственных за код, художественную оценку и выпуск; один человек может совмещать роли. Приёмка: агент не выдаёт себе human approval. Evidence: [роли, human boundary и точные hashes](production/REVIEW_ROLES.md); коммит `roadmap(009)`.
10. [ ] **Измерить исходный результат.** Записать время до первого usable-экспорта, число ручных исправлений, частоту успешных сеансов и оценки моделей. Приёмка: последующие улучшения сравниваются с этим baseline. В работе: [core benchmark](production/BASELINE_MEASUREMENTS.md); actual agent/user/art observations ещё не получены, пункт не закрыт.

93. [ ] **Исправить причины дефектов пилота.** Приоритизировать потерю данных, слабое качество моделей, ошибки интеграции и непонятные отказы. Приёмка: исправление попало в compiler/pack/service и подтверждено повторением сценария.
94. [ ] **Подготовить Windows-дистрибутив.** Проверить выбранный installer/portable, чистую установку, обновление и удаление. Приёмка: пользовательские проекты сохраняются, рабочая версия не перезаписывается запущенным тестом.
95. [ ] **Собрать полный release bundle.** Включить JAR, sources, editable assets, docs, licenses, SBOM, provenance и hashes. Приёмка: отдельная verify-команда подтверждает состав и связь с принятыми кандидатами.
96. [ ] **Подтвердить подлинность и воспроизводимость.** Настроить Windows signing и сравнение независимых locked builds. Приёмка: проверяемая подпись и digests; влияние timestamps/подписания на byte-level comparison документировано.
97. [ ] **Реализовать безопасные обновления.** Разделить beta/stable, проверять подпись/digest, поддержать rollback и миграцию проекта. Приёмка: обновление согласовано пользователем и его прерывание не уничтожает рабочую версию.
98. [ ] **Подготовить документацию и поддержку.** Русский quickstart, подключение обоих агентов, ограничения, восстановление и bug-report template. Приёмка: новый пользователь повторяет путь без помощи разработчика; есть процедура triage и patch-релизов.
99. [ ] **Заморозить release candidate.** Зафиксировать исходную revision, пакеты, версии, evidence index и approvals точных hashes. Приёмка: CLI/MCP дают согласованный workflow, все проверки перед публикацией закрыты и нет блокирующих findings.
100. [ ] **Выпустить production-версию по явному решению человека.** Сначала `publish_prepare`, затем отдельная публикация согласованного digest. Приёмка: доступны проверенные артефакты, changelog, инструкции и канал обратной связи.

## Как закрывать пункты

К отметке `[x]` приложить результат, точную revision/версию, команду или сценарий проверки и ссылку на evidence. Для художественных задач требуется human review; для игровых — результат на Fabric 1.20.1, а не только editor render. Связанное изменение ассета аннулирует старое art approval. Изменение compatibility pack требует соответствующей повторной проверки. Успешная публикация редактора beta не закрывает игровые пункты автоматически.

Ближайшая полезная итерация: дополнить уже заданные брифы и критерии фактическими измерениями (10), принять качественный силуэт одного оружия (41–46), добавить адресное улучшение с сохранением ручной работы (38), затем провести reviewed-интеграцию оружия и одного блока в 1.20.1 (49, 58, 62–66, 71–76). Существующие агентные сеансы, сохранение и CI имеют свои evidence; изменения этих компонентов требуют проверки нового кандидата, а не повторного закрытия прежнего пункта.
