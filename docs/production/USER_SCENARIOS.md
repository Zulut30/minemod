# Пользовательские сценарии первого выпуска

Roadmap: пункт 002. Контракт платформ: [RELEASE_CONTRACT](RELEASE_CONTRACT.md).

Сценарии ниже описывают требуемое поведение. Они не являются отчётом о пользовательском пилоте. Реализованные операции сверяются с editor service и HTTP MCP; отсутствующие операции остаются задачами roadmap.

## Сценарий A: новичок создаёт предмет с агентом

**Начало:** установлены Studio и один из клиентов Codex/Claude Code; пользователь уже вошёл в свой клиент. Новый проект создаётся в Studio. Создание arbitrary-проектов или путей через MCP не требуется.

**Шаги:**

- Пользователь задаёт назначение, стиль и ограничения оружия: например, короткий ледяной топор с читаемым Minecraft-силуэтом.
- Studio показывает структурированный бриф и включённые права. Пользователь включает локальное подключение и получает актуальную настройку клиента; секрет остаётся вне проекта и экспорта.
- Агент читает проект, IDs, revision и закреплённые части. Предлагает варианты формы, используя разрешённые операции.
- Пользователь сравнивает геометрию с общим масштабом и светом, смотрит силуэт и 32/64 px, выбирает направление.
- Агент исправляет отмеченную часть по реальному capture. Пользователь вручную меняет цвет или рисунок; остальные части сохраняются.
- Пользователь сохраняет проект, повторно открывает его, проверяет результат и экспортирует bundle после технической проверки.

**Ожидаемый результат:** editable проект, выбранный вариант, runtime JSON/PNG/source, технический отчёт и явно незакрытая либо выполненная художественная приёмка. Экспорт не выдаёт ложный статус «проверено в Minecraft».

**Ошибки и восстановление:**

| Ситуация | Ответ продукта | Что пользователь может сделать |
|---|---|---|
| Клиент отсутствует или не авторизован | Понятная причина в панели подключения | Настроить свой клиент; ручной редактор продолжает работать |
| Устарел токен | Подключение прекращается; сцена не изменяется | Получить новую настройку текущего сеанса |
| Агент использует старую revision | Предложение отклоняется без перезаписи | Перечитать проект и пересчитать предложение |
| Нужная часть закреплена | Точная диагностика запрета | Изменить права осознанно или выбрать другую часть |
| Некорректная геометрия/лимит | Назван нарушенный target/лимит | Исправить указанную часть либо отменить транзакцию |
| Сбой/отмена агента | Сохраняются ручные изменения и корректный checkpoint | Продолжить сеанс или работать вручную |
| Слабый художественный результат | Candidate остаётся DRAFT/NEEDS_REPAIR по правилам review | Дать конкретное замечание; выбрать другой вариант |

**Проверка:** повторить весь путь отдельно в Codex и Claude Code без записи geometry напрямую в файл или подмены экспортируемого результата. Фактический пилот закрывается пунктами 31–32 и 92, а не этим описанием.

## Сценарий B: автор мода редактирует и интегрирует ассет

**Начало:** у автора есть собственный Studio-проект, ModSpec под Fabric 1.20.1 и разрешённая новая область для generated workspace. Экспорт из редактора и сборка мода имеют разные границы.

**Шаги:**

- Автор открывает проект, проверяет target и фиксирует части/рисунок, которые нужно сохранить.
- Вручную меняет пропорции, материал и UV; undo/redo возвращает все данные, включая пиксели и варианты.
- При необходимости агент получает право исправить только незакреплённые части. Ручная правка и proposal используют одну revision-проверку.
- Автор экспортирует versioned bundle и получает точные hashes, editable source, diagnostics и provenance.
- Reviewed bundle явно связывается с ModSpec. Application/compiler проверяют resource references; trusted pack не изменяется ради подключения модели.
- Разрешённый Linux runner собирает новый workspace по закрытому BuildPlan. Выполняются обязательные build, client/server и игровые визуальные проверки.
- После технической и человеческой художественной приёмки создаётся release bundle; публикация выполняется отдельной операцией.

**Ожидаемый результат:** читаемый generated Fabric-проект, JAR, sources, редактируемые ассеты, отчёты и подтверждённая связь принятой модели с ресурсами в игре.

**Ошибки и восстановление:**

| Ситуация | Ответ продукта | Продолжение |
|---|---|---|
| Bundle ещё не поддержан компилятором | `SPEC_UNSUPPORTED` или более точный diagnostic | Сохранить экспорт; не обходить контракт подменой JAR |
| Нет разрешённого Linux runner | Отдельное сообщение об окружении сборки | Редактирование/экспорт остаются доступны; настройка runner выполняется явно |
| Путь занят user-owned файлами | Транзакция отклоняется | Выбрать новую область без удаления существующего проекта |
| Неверная ссылка или namespace | Назван конкретный missing/invalid resource | Исправить источник и пересобрать bundle |
| Сбой build/runtime | Отчёт остаётся failed, файлы автора не перезаписываются | Исправить generator/contract, затем повторить проверки |
| Изменились принятые файлы | Старое approval становится неприменимым | Создать и оценить новый candidate |

**Проверка:** пройти путь из clean input без ручной правки generated Java/JAR. Текущие отсутствие reviewed asset integration и непроверенный Windows→runner workflow остаются явными gaps до пунктов 61–80.

## Приёмка пункта 002

Для обоих сценариев названы исходные условия, последовательность, конечные артефакты и восстановление после ошибок. Описание согласовано с существующими revision, selection, capture, export и connection boundaries. Сценарий нельзя считать runtime PASS только из-за появления этого документа.
