# Autosave и восстановление проекта

Roadmap 026. Проверено на Windows x64 с Node 24.11.0 и упакованным Studio 0.5.1. [Evidence](evidence/autosave-026.json) связывает исходники, test logs, packaged report и SHA-256 `app.asar`.

Worker последовательно сохраняет подтверждённое состояние сессии. Для текущего проекта и `.bak` используются отдельные случайные staging files рядом с целевым файлом: exclusive `wx`, ограниченная проверка проекта, запись, `sync`, закрытие, затем `rename`. Backup содержит последнюю корректную версию основного проекта; повреждённый основной файл не заменяет корректный backup. При ошибке публикации backup основной файл не заменяется.

Временные файлы помечаются как owned только после успешного exclusive open. При обычной ошибке очищаются только staging files текущей операции. После принудительного завершения процесса `.pending` может остаться; он не считается успешным сохранением и не импортируется автоматически. Очистка чужих файлов ради восстановления не выполняется.

При старте worker читает основной recovery project, затем пробует `.bak`. UI сообщает о восстановлении из backup. Если обе копии повреждены, исходные файлы сохраняются; приложение показывает ошибку. Ошибка autosave остаётся видимой до успешного повторного сохранения; доступно ручное сохранение в выбранный пользователем файл.

## Проверенные сценарии

| Проверка | Фактический результат |
|---|---|
| Принудительное завершение дочернего процесса посреди записи основного staging file | Primary и старый backup сохраняют прежние bytes; неполный staging не проходит parse |
| Завершение посреди записи staging backup | Primary и отличающийся старый backup не меняются; частичный `.bak` не публикуется |
| Завершение после готового backup, перед заменой primary | Primary остаётся корректным, backup содержит полную предыдущую primary-версию |
| Retry после каждого завершения | Новый проект корректно сохраняется, backup содержит прежний primary |
| Невозможная публикация backup: целевой `.bak` является директорией | Save отказывает, основной проект сохраняется, staging текущего вызова очищается |
| Повреждённый основной проект | Корректный backup не перезаписывается повреждёнными данными |
| Packaged restart, backup-only recovery, повреждение обеих копий, ошибка recovery write | Состояние восстановлено либо ошибка показана; исходные повреждённые данные не уничтожены |

Crash tests завершают только собственные Node children в отдельном временном каталоге. Packaged E2E запускает собственные скрытые Electron-процессы с отдельным user data; пользовательское приложение не закрывается.

Границы доказательства: это process-crash tests и runtime recovery на Windows. Физическое отключение питания, гарантии дискового контроллера, directory fsync, disk-full и несколько независимых writers этим отчётом не подтверждены. Одна `.bak` не заменяет version history; версии модели существуют внутри проекта. Дополнительные аварийные и resource-limit сценарии остаются в пунктах 078/089.

Выбор exclusive write, `FileHandle.sync` и последовательного `rename` сверён с [Node.js fs API](https://nodejs.org/docs/latest-v24.x/api/fs.html) и Context7. `copyFile` не предоставляет атомарности записи; direct copy backup заменён staging/rename без новой runtime dependency.
