# Улучшение кода и authored 3D-моделей

Текущий пример — вторая версия меча «Северное сияние» для формата предметов Minecraft Java 1.20.1. Исходник `fixtures/assets/aurora-longsword-v2.mjs` задаёт геометрию и авторскую пиксельную покраску; он сохраняет закрытый JSON `aurora-longsword-v2.item-asset.json`. Экспортёр принимает только данные из этого JSON.

Первая версия сохранена в `aurora-longsword.item-asset.json` для сравнения. У неё прямоугольный клинок, тяжёлая гарда и четыре одинаковые пары объёмных рун. Во второй версии клинок сужается к острию, гарда тоньше и направлена к рукояти, руны нарисованы в центральном доле, главный акцент — небольшой кристалл. 52 куба включают ступени острия; количество деталей само по себе не оценивает качество.

## Что поручать Codex

Агент сам выбирает силуэт, пропорции, детали, палитру и раскладку кубов. Экспортёр проверяет формат, а не придумывает дизайн за агента. Качество оценивают по виду целого предмета, читаемости на небольшом размере и совместимости с визуальным стилем модпака.

Для покраски есть два контракта: прежний `CuboidTexturePlan` с материалами и узорами и новый `ItemPixelTexturePlan` с явно заданными пикселями и UV каждой грани. Во второй версии плотность составляет примерно четыре пикселя на единицу модели, атлас — 256×256. Увеличение атласа помогает только тогда, когда UV действительно выделяет поверхности больше пикселей. Бирюзовые руны используют цвет; emissive-рендер, normal maps и анимация в этом пути не реализованы.

Практический цикл:

1. Зафиксировать brief: тип предмета, стиль, размер в руке, основной силуэт и 2–3 характерные детали. Для нескольких вариантов менять дизайн, сохраняя назначение предмета.
2. Авторить `model` и `texturePlan` как данные, используя закрытые схемы. Не вставлять Java, shell или исполняемые Blockbench-скрипты в payload.
3. Выполнить экспорт. Исправить каждую конкретную ошибку координат, UV или поворота; не округлять неподдерживаемый угол молча.
4. Создать preview, посмотреть спереди, сбоку, сзади и в три четверти; вращением проверить стыки и пересечения. Проверить каркас и маленький силуэт. Сохранить снимки.
5. Исправить видимые проблемы и повторить экспорт. Не считать успешную схему или большое количество деталей доказательством красоты.
6. После принятия дизайна интегрировать ресурсы через явный контракт сборки и проверить инвентарь, обе руки, вид от первого/третьего лица и отсутствие client-only зависимостей на dedicated server.

Пример покрывает пункты 1–5. Для пункта 6 ещё нужен проверенный путь подключения authored asset bundle к Fabric compiler.

## Запуск

Требуются установленные workspace-зависимости и Node.js 24.11.0. Новых внешних runtime-зависимостей этот путь не добавляет.

```bash
node scripts/preview-item.mjs
# После редактирования авторского источника второй версии:
node fixtures/assets/aurora-longsword-v2.mjs
node scripts/preview-item.mjs
# Первая версия для сравнения:
node scripts/preview-item.mjs fixtures/assets/aurora-longsword.item-asset.json output/item-preview
```

Откройте полученный `preview.html` обычным браузером. HTML включает геометрию и PNG, поэтому сеть не требуется. Скрипт записывает файлы в выбранный каталог и при повторном запуске обновляет их; используйте отдельный `output/`-каталог. Это локальный инструмент разработчика, а не MCP-доступ к файловой системе.

В каталоге будут:

- `assets/mcdev/models/item/aurora_longsword_v2.json` — нативная геометрия предмета;
- `assets/mcdev/textures/item/aurora_longsword_v2.png` — атлас 256×256;
- `editable/mcdev/aurora_longsword_v2.bbmodel` — редактируемый Blockbench 5 project;
- `source.item-asset.json` и `bundle.json` — исходник и результат с SHA-256;
- `preview.html` — текстурированный просмотр с вращением, масштабом и каркасом.

Файл `.bbmodel` использует формат `java_block`, точные UV каждой грани и стартовые display transforms из игрового JSON. Это сохраняет дробные размеры тонких рун и обмоток: обычный box UV в редакторе может округлить такую грань до нулевой высоты. Игровой JSON создаёт отдельный экспортёр; открытие проекта Blockbench ещё не доказывает работу предмета в игре.

Просмотр использует ортографическую проекцию и проверку глубины каждого пикселя. Он помогает оценить геометрию и текстуру, но не воспроизводит игровой свет, display transforms, mipmaps и позу игрока.

## CLI и MCP

CLI-команда `mcdev asset item '<inline-json>'` и MCP-инструмент `mcdev_asset_compile_item({ payload: "<inline-json>" })` вызывают один application service. Корневой объект содержит строго четыре поля:

```typescript
type ItemAssetRequest = {
  schemaVersion: 0;
  kind: "minecraft-item-asset";
  model: CuboidModelSpec;
  texturePlan: CuboidTexturePlan | ItemPixelTexturePlan;
};
```

Типы определены в `@mcdev/assets-contracts`; полные валидные JSON находятся в fixtures. `ItemPixelTexturePlan` содержит `palette` из максимум 32 пар `{ symbol, color }`, `rows` и `faces`: для каждого `cubeId` задаются шесть прямоугольников UV в пикселях. Символы `0–9`, `a–v` обозначают цвета `#RRGGBB`, точка — прозрачность. Строки точно соответствуют размерам атласа до 256×256. Символы и назначения кубов уникальны; неизвестные цвета, отсутствующие назначения, UV нулевой площади или за пределами атласа отклоняются. Перевёрнутые UV допустимы.

Ограничение входа — 262144 байта UTF-8. Результат имеет `kind: minecraft-item-asset-bundle`, `reviewRequired: true` и три файла с относительными путями, кодировкой `utf8`/`base64`, содержимым и SHA-256. CLI/MCP возвращают данные без записи ресурсов, регистрации предмета или запуска Gradle. Некорректный запрос получает диагностическую ошибку; неожиданные внутренние ошибки не раскрывают путь к рабочей папке.

## Ограничения нативного экспорта 1.20.1

- Только `held-item`, с непустой геометрией. 3D-броня на игроке требует отдельного renderer и другого acceptance path.
- Координаты `from/to`, включая `inflate`, находятся в диапазоне −16…32.
- Куб вращается вокруг одной оси на 0, ±22.5 или ±45°. Произвольные группы с поворотами отклоняются; геометрия задаётся в общей исходной позе.
- Box UV задаётся в пикселях атласа и экспортируется в единицы Minecraft 0…16, отдельно для ширины и высоты. Поддерживаются зеркальные UV.
- Рендер `CuboidTexturePlan` требует целых размеров развёрнутой box UV и одного назначения материала на куб. `ItemPixelTexturePlan` использует независимые UV каждой грани и поддерживает дробную геометрию без округления толщины. При авторинге оставляйте промежутки и продолжайте цвет края за границы UV, чтобы уменьшить просачивание соседних цветов.
- JSON с явными `elements` не получает `item/generated` или `item/handheld` parent. Положение предмета задают стартовые display transforms; их качество ещё нужно оценить в игре.

Описание box UV и поведения экспортёра проверено по официальным исходникам [Blockbench 5 cube UV](https://github.com/JannisX11/blockbench/blob/v5.0.0/js/outliner/cube.js), [Java model format](https://github.com/JannisX11/blockbench/blob/v5.0.0/js/io/formats/java_block.js) и [формата проекта bbmodel](https://github.com/JannisX11/blockbench/blob/v5.0.0/js/io/formats/bbmodel.js), а также Context7. Эти источники использованы для проверки формата; сторонние геометрия, текстуры и код не копировались. Новые версии Minecraft могут поддерживать другие ограничения — профиль 1.20.1 от этого автоматически не меняется.

## Качество кода

Один тип результата и один application service обслуживают CLI и MCP; слой экспорта работает без файловой системы и сборочного runner. Граница формата отделена от визуального review. Это позволяет улучшать дизайн без изменения trusted compatibility pack и чинить экспорт небольшими проверяемыми изменениями.

При следующей работе:

- читать текущий Fabric baseline, сохраняя main/client separation;
- ограничивать входные данные и проверять строгие контракты на границе;
- возвращать диагностические предупреждения вместе с результатом сборки; `PLACEHOLDER_ASSETS_USED` должен быть виден пользователю;
- сохранять детерминированный результат и проверять хеши;
- добавлять тесты на ошибки, которые реально меняют результат: ориентацию UV, отрицательные углы, границы inflate, закрытые payload и передачу предупреждений;
- запускать lint, typecheck и затронутые тесты, затем реальные build/GameTests/server checks на поддерживаемой среде;
- отдельно записывать, что проверено исходниками, mock, браузером и самой игрой.

В этом checkout исправлен Windows-запуск Corepack в MCP-тесте: JavaScript entrypoint запускается через Node вместо прямого `spawnSync` `.cmd`. Это позволяет выполнять протокольные проверки на Windows. Ограничения Linux build runner и POSIX file modes остаются; их нельзя представлять как проверенный Windows → JAR путь.
